## 1. 检索双词复核规则（不存在性结论的举证门槛）

**规则：凡用 grep 得出「不存在 / 无调用 / 死代码」的结论，必须换第二个等价但形式不同的词再查一次，两个词都零命中才允许下结论。**

血案：`grep "resolveApproverLevel("` 只命中定义处 → 误判死代码并建议删除；真相是调用点写作 `this.resolveApproverLevel(user)`（`borrow.service.ts:269`）。`this.` 前缀、解构赋值、别名 re-export 都是精确检索词的盲区。

常见逃逸写法对照（下「不存在」结论前，左右两列都要查）：

| 第一检索词 | 必须补查的第二形式 |
|---|---|
| `foo(` | `this.foo(` / `.foo(` / **`foo`（裸词，无符号）** |
| `import { foo }` | `import * as` / `require(` / 别名 re-export |
| 函数名 | 接口/类型名（可能以类型形式被引用） |
| 常量名 | 其字符串字面值（可能被动态拼接引用） |

> **更保守一档的标准（工程师实践，采纳）**：带语法符号的检索词，符号本身就是盲区——`foo(` 会漏 `this.foo(`、`?.foo(`、`(foo)(x)`、跨行调用，逐个列举穷举不完。下「不存在」结论前，用**不带任何语法符号的裸词**搜一遍全仓并人工过一遍命中，一次全覆盖所有调用形态。

## 2. 断言强度分级（L1–L5）与强度下限规则

| 级别 | 形态 | 证明力 |
|---|---|---|
| L1 | `expect(...).toThrow()` | 几乎不证明任何事（任何错误都能过） |
| L2 | `toThrow(SpecificError)` | 证明错误类型，不证明来源 |
| L3 | code + 文案双断言 | 能区分拒绝来源（如 `code=1003` + `无权办理` + `第 2 级` 区分能力校验 vs 次序校验） |
| L4 | L3 + 副作用检查 | 证明「被拒且未留痕」/「状态未变」等反向不变量 |
| L5 | L4 + 变异验证 | 证明测试真的能抓住防线被拆除（见 §5） |

**强度下限规则（PM 定）：断言强度下限 = 防线被绕过的业务后果等级；合规红线类防线必须 L4 起步，关键防线标配 L5。**

对应到本项目：
- 审批三道闸门（次序/能力/重复签署）、撤权即时生效、权限变更入口清单 → **L5**（已做双向变异验证）
- 参数生效模式（D-1）、固化参数拒改 → **L4** 起步
- 普通 CRUD happy path → L3 即可

**禁止事项**：安全相关用例停留在 L1/L2。`toThrow()` 通过的测试不能作为任何防线存在的证据。

### 2.1 附则：宽松正则是「验证概率」，不是「验证语义」

宽松正则的问题不在强度等级，而在于它把断言从「验证语义」降格成「验证概率」：`/D-1|允许分组|不可/` 三个分支任一命中就过——它测的不是「borrow 组不允许 retention」这条规则，而是「某个我猜得到的词碰巧出现在某处」。用例的通过与否取决于实现者的选词习惯，而不是防线是否成立。

**自检判据（换词实验）**：把正则逐分支拆开，问每个分支——「如果实现者换一个同义词表达同一规则，这个分支还命中吗？」任一分支答「否」，说明它依附措辞而非规则，属概率性断言。正确做法：**先读源码确认防线在说什么，再决定断言测什么**——断言的动作从「猜文案」改成「引用规则」。

```ts
// ✗ 概率性：三个分支全依附措辞，换词即失效
expect(() => assertParamDefs([bad])).toThrow(/D-1|允许分组|不可/);

// ✓ 语义性：类型锚定 + 两个规则要件（不允许 + 分组名）
expect(() => assertParamDefs([bad])).toThrow(ParamDefConfigError);   // 类型锚定，不可省
expect(() => assertParamDefs([bad])).toThrow(/不允许\s*effectiveMode/);
expect(() => assertParamDefs([bad])).toThrow(/borrow/);
```

> **类型锚定不可省**：内容正则单独用，仍可能被一个碰巧带相似文案的无关 `TypeError` 蒙混过关。`toThrow(SpecificError)` 保证「被拒」的原因是这个防御机制触发。

**同类陷阱（多实例 C-5 实战）**：断言「B 读到新值」测不出广播通道——版本号换 key 会让它无条件变绿；**断副作用不等于断生产代码的副作用**——如果断言打在测试自建的替身订阅者上，生产 `handlePermissionInvalidate` 根本没进路径。必须走真实订阅路径（`onModuleInit`），并加前置断言证明「订阅真的建立了」（生产侧订阅失败只记日志不抛，静默失败是设计，测试必须主动验证）。

## 3. 「建议删除」类结论的举证责任

**举证责任：提出「这段代码是死的、建议删除」的人，举证标准高于「发现一个缺陷」。**

删除建议一旦被执行，防线就没了。因此：
1. 必须先完成 §1 的双词复核；
2. 必须排除中间层间接调用（基类、装饰器、反射、模板字符串拼接）；
3. 结论表述必须写明检索方式与覆盖范围，例如「以 X、Y 两词全仓检索零命中，且未发现有反射/基类调用路径」；
4. 存疑时表述为「疑似未被调用，请 Engineer 确认」，而不是「死代码，建议删除」。

## 4. 夹具语义同构陷阱（测试假绿/假红高发区）

夹具「看起来等价」但语义不同，是测试自身 bug 的最大来源。本项目已踩过的坑，禁止再犯：

| 陷阱 | 错误写法 | 正确写法 | 症状 |
|---|---|---|---|
| Reflector 元数据不沿原型链 | `reflector.get(KEY, handler)` | `reflector.getAllAndOverride(KEY, [handler, class])` | Guard 永远拿不到元数据，整组假绿 |
| ErrorCode 是对象不是数字 | `expect(e.code).toBe(ErrorCode.FORBIDDEN)` | `expect(e.code).toBe(ErrorCode.FORBIDDEN.code)` | 恒红/恒绿（对象与数字永不相等） |
| checkScope:false 接口跳过密级校验 | 拿 `listItems` 测密级拦截 | 用 `checkScope:true` 的接口（如 `itemDetail`） | 密级防线「看起来失效」，差点误报源码 bug |
| 方法体 includes 被注释误判 | 裸 `body.includes('invalidateSnapshot')` | 先剥块注释/行注释再正则匹配 | 注释里提一句就误判为「已调用」 |
| 次序校验遮蔽能力校验 | 在 `currentLevel=1` 单据上测终审权限 | 单据必须先推进到 `currentLevel=2` | 被第一道闸门先拦，测不到目标闸门 |

**通则一**：测试失败时，先怀疑夹具语义，再怀疑实现；下「源码 bug」结论前，必须用最小复现确认失败路径确实经过目标代码。（最终回归再添一例：用 `new Map()` 充当 `Record` 型 ParamView，`view[key]` 恒 undefined → C-1 假阴性。）

**通则二（串联防线测试，工程师建议采纳）**：多道串联防线里，测后一道必须先满足前一道。每条用例必须先声明它在测哪一道闸门，并断言拒绝理由指向该闸门（code + 文案），而非只断言「被拒」。这也是 §2 中 L3 双断言的由来。

## 5. 变异测试最小实践（关键防线标配）

**规则：凡守护合规红线的测试组，必须做一次「亲手拆防线 → 测试必须红」的反向验证。**

最小流程：
1. 在源码防线处注入一个显式错误（推荐加 `// MUTANT` 注释便于收尾清点）；
2. 跑目标测试组，**必须**有红，且红的位置符合预期；
3. 恢复源码；
4. `grep -rn "MUTANT" --include="*.ts"` 必须 0 命中（收尾检查，防变异残留进主干）。

本项目已执行并留档的变异结果：
- `resolveApproverLevel` 注入 `return 2`（人人可签终审）→ 6 红；注入 `return 1`（无人可终审）→ 5 红（双向夹逼，证明用例锁定的是「恰好 R4」而非「随便一个阈值」）
- 删 `updateUserScopes` 的 `invalidateSnapshot` → CI 静态脚本 EXIT=1 且精确定位入口
- 把 `borrow.approve.self-check` 塞进正清单 → 一致性守卫 1 红（证明检查器真的读取排除列表）

**测试组全绿本身不构成防线有效的证据；「拆了会红」才构成。**

### 5.1 变异「0 红」时的排查顺序（按概率从高到低）

注入变异后全绿，不要急着加强断言——按以下顺序排查，**前两步都是「对象错了」，加强断言无解**：

**① 断言对象是否在生产路径上？（替身陷阱）**
断言形态正确，但打的是测试自建的替身，生产代码根本没进路径。
> 案例（多实例 C-5）：测试自己写订阅者回调照抄 `handlePermissionInvalidate` 逻辑去清缓存，断言「缓存被清空」——形态对，但删掉生产那 25 行替身照跑，变异 0 红。修法：夹具补全 `duplicateForSubscribe/subscribe/on/quit`，让用例走真实 `onModuleInit` 订阅。
> **衍生坑**：生产侧「订阅失败只记日志不抛」是合理降级，但意味着测试不能把「onModuleInit 没抛异常」当「订阅成功了」——静默失败会被 try/catch 吞掉。必须有前置断言证明通道真的建立了。

**② 断言是否被另一条防线掩护？（搭便车假绿）**
被测防线失效时，另一条独立防线会兜出同样的可观测结果。
> 案例（多实例 C-5）：断言「B 读到新值」测广播通道——但 `getSnapshot` 每次实时读版本号算 key，v0/v1 key 天然失配，版本号通道让该断言无条件变绿。禁用 `handlePermissionInvalidate` 后 17 条照绿。修法：改断**该防线独有的副作用**（广播 → 进程内缓存被清空），并给每条用例声明「在测哪道闸门」。

**③ 断言强度是否不足？（措辞依附）**
前两项排除后，才轮到收紧断言（类型锚定、精确正则、副作用检查），见 §2 与 §2.1 换词实验。

**判据**：变异红数应与该防线守护的用例数**精确匹配**——少了说明有用例空转或打错对象，多了说明用例间耦合过深、失败信号无法归因。（实证：禁用广播处理 → 恰好红 T2 一条；禁用版本号 INCR → 恰好红 3 条，T2/T3 保持绿，证明两通道互不遮蔽。）

## 6. 基线管理

- 当前基线：**418 总 / 418 通过 / 0 skip**（多实例 C-5 启封 T 类 3 条 + 压测判据单测 19 条，skip 清零）。
- 基线数字变动必须说明来源：新增测试组、删并、还是工程师顺手补充；QA 对「莫名其妙的 +N」必须逐条核验，不允许「反正绿了」。

### 6.1 工具默认行为的静默陷阱（「以为改对了其实没改对」家族）

- **vitest 必须在仓库根执行**：`apps/api` 子目录下跑 `vitest` 会因 `include` 路径（仓库根相对）静默匹配 **0 个用例**——比红更危险的是「以为跑了」。
- **文档提交前看 `git diff --numstat`**：行数远超预期（如改 57 行却显示 611 行变更）通常是**行尾被翻转**（Windows 下 Python `io.open(w)` 默认把 `\n` 写成 `\r\n`）。行尾翻转会让 merge 冲突爆炸、`git blame` 全篇失效。修法：二进制模式读写或 `data.replace(b'\r\n', b'\n')` 还原后核对。
- **`git checkout -- <文件>` 做变异恢复是核武器**：它会恢复 HEAD 版本，**冲掉他人未提交的工作区改动**（本项目实战事故：工程师未提交的第 7 项实现被误抹）。变异恢复改用注入时的反向替换（怎么注入就怎么改回），或对共享文件先确认归属。
