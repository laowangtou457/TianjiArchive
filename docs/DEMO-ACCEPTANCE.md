- **预期**：三账号均登录成功、工作台按角色呈现（`PRD.md` §8.2 ①）；R3 访问参数页返回 403 并记日志。

#### S2 建全宗 / 案卷 / 件三级著录

- **预期**：三级层级正确、件级必填校验生效（缺必填项不能保存）、卷内序号自动排序、一件一档号；`档号*、题名*、责任者*、形成日期*、年度*、保管期限*、密级*、页数/件数*` 八项核心必填齐全。
- **验收判据**：`PRD.md` §5.1 F-01「全宗号全局唯一」、F-03「著录字段符合表 F-03-1 字段集；保存含必填校验」、F-04「件级必填项校验通过；一件一档号；卷内序号自动排序」；§6.2 合规底线①「核心著录字段不可由用户随意裁剪」。

#### S3 档号自动生成与唯一性

- **操作**：在 S2 新增件时观察档号自动生成；再连续新增 ≥20 件，核对编号连续、无重号；到「档号规则配置」页（`PRD.md` §8.2 ② 顶部）做一次**只读试算**，不保存规则。
- **预期**：新著录 100% 按 seed 默认模板生成；连续编号无重号、无断号；试算结果与实际生成一致。
- **验收判据**：`PRD.md` §5.1 F-02「规则保存后新著录 100% 按规则生成；并发生成无重号（唯一约束 + 序列锁）」；§2.2 **M5**「档号生成 100% 符合配置的 DA/T 22 规则，冲突为零」；§6.2 F-02 行「生成结果对照标准样例表」。
- **如果失败，唯一原因是什么**：demo 全宗未绑定档号规则（或规则被误配）。S2 已锁定著录链路与层级，S0-4 已锁定规则引擎可用；**注意本步只读试算、不保存规则**，因此不存在「规则改坏」这一变量。若出现重号，属 F-02 真实缺陷，须按 §5.2 判不通过并单独上报，不得继续。

#### S4 电子文件上传挂接（含跨分片）—— **本次 demo 的核心步骤**

- **操作**：在 S2 的某一件上挂接电子文件：① 上传 1 个 ≤5MB 的**含文本层模拟 PDF**（整对象 PUT）→ ② 上传 1 个 **>5MB 的 PDF**（触发 5MB 分片，验证 SeaweedFS multipart 合并）→ ③ 上传 1 个图片扫描件 → ④ 上传 1 个内容与扩展名不符的文件，验证拒绝。上传后查看文件列表的 sha256 / 大小 / 抽取状态。
- **预期**：①② ③ 成功入库且服务端重算 SHA-256 记入 `electronic_file`；④ 被魔数嗅探拒绝且不落库；>5MB 文件分片合并后对象大小与源文件一致。

**附：模拟样本脚本输出名的读法（QA 复核反馈，防两种误判）**

`apps/api/src/scripts/demo-books-seed.ts` 会打印 `PRESIGNED_DOWNLOADS_OK` / `PREVIEW_DOWNLOADS_OK`。经双向复核（脚本实读 + 全域检索 `grants` / `PermissionSnapshot` / `/api` / `file.service` 均无引用），该段是**纯 S3 wire 自检**：直接 `client.presignedGetObject` → `fetch` → 长度与 SHA-256 比对，**不经 `file.service.download()` 鉴权、不构造 `DOWNLOAD` 授权、不请求 `/api`**。据此两条口径：

| 风险 | 口径 |
|---|---|
| **假绿**（把 wire 自检读成「下载功能已验证」） | 该输出属 **D-4 技术层**，只支持写「S3 协议下载技术链路已验证」；**不得**写进「下载功能已验证」或「下载受控通过」，也不得与业务层结论合并。输出名含 `DOWNLOADS_OK` 易误读，交付说明与试用报告须按本表语义标注（QA 已同步工程师，脚本侧是否更名不影响本口径）。 |
| **假红**（把 wire 自检读成「绕过缺陷制造下载成功」） | 该输出**不构成** §5.1 不通过条件⑤所指的「以任何绕过手段制造下载成功」，**不得按重大偏差处理**。⑤约束的是「通过业务鉴权路径拿到下载放行」，而脚本根本没走业务鉴权路径。 |

> 这一对风险是同一事实的两面：**既不能拿它当下载可用的证据，也不能拿它当违规的证据**。它只是 D-4 两层中的技术层证据。
