## 2. 产品定义

### 2.1 Product Goals

1. **业务可替代**：在不依赖原厂商的前提下，完整承载单位档案"收—管—用—存"全流程，做到现有 DARMS 系统停用后业务不中断、不降级。
2. **标准可合规**：档号生成规则与著录字段严格对齐 DA/T 22、DA/T 18 等标准，交出能被上级档案主管部门检查验收的数据。
3. **使用可高效**：百万级馆藏 + 百 GB 电子文件条件下保持"秒级检索、即点即看"，100 人同时在线著录/检索/预览不掉速，把日常操作步数压到最少。

> 三条目标相互正交：目标 1 解决"有没有"，目标 2 解决"合规不合规"，目标 3 解决"好不好用"。

### 2.2 成功指标（验收口径）

| 编号 | 指标 | 目标值 | 度量方式 |
|---|---|---|---|
| M1 | 现有档案数据迁移完整率 | 100%（条目数、文件数、档号一一对应，抽查 200 条零差错） | 迁移后自动比对报告 |
| M2 | 核心业务闭环可用性 | 著录→归档→检索→借阅→归还 全链路 100% 走通，无人工干预 | UAT 用例全通过 |
| M3 | 检索性能 | 全文检索 P95 < 2s；条件检索 P95 < 1s（百万条目 + 100GB 文件基线） | 压测报告 |
| M4 | 并发能力 | 100 用户混合负载下错误率 < 0.1%，P95 响应 < 3s | JMeter/Locust 压测 |
| M5 | 档号合规 | 档号生成 100% 符合配置的 DA/T 22 规则，冲突为零 | 抽检 + 唯一性校验日志 |

| M7 | 数据安全 | 每日自动备份成功率 100%，RPO ≤ 24h，RTO ≤ 4h | 备份报表 + 恢复演练 |

## 3. 用户角色与权限矩阵

### 3.1 角色定义

| 角色 | 说明 | 典型人数 |
|---|---|---|
| R0 系统管理员 | 负责系统配置、账号、参数、备份与运维，**原则上不接触档案内容**（可由档案管理员兼任） | 1-2 |
| R1 档案管理员 | 档案业务主责人：全宗建档、著录、归档、编研、鉴定、统计、借阅审批 | 3-8 |
| R2 部门兼职档案员 | 本部门文件收集、初步著录、提交归档（限定本部门全宗/机构范围） | 10-30 |
| R3 借阅用户（普通用户） | 检索、查阅、发起借阅申请、查看本人借阅记录 | 全体职工 |
| R4 领导/查档审批人 | 查阅统计与报表、审批重要/敏感档案借阅 | 2-5 |

## 4. 用户故事

**R1 档案管理员**
- US-1：作为档案管理员，我要能新建全宗并配置其档号生成规则（全宗号 + 目录号 + 年度 + 保管期限 + 件号/卷号，可自定义分隔符与位数），以便新接收的档案能自动获得合规且唯一的档号，不必手工编号。
- US-2：作为档案管理员，我要能先建案卷、再在卷内逐件著录，系统自动带出卷级公共字段（全宗、年度、保管期限、责任者），以便一次接收上百件文件时著录不重复劳动。
- US-3：作为档案管理员，我要能一键把扫描件 PDF/图片/音视频挂到条目上并在线预览（PDF 翻页、图片放大、音视频播放），以便核实著录与原件是否一致。
- US-4：作为档案管理员，我要能按"任意字段组合 + 全文关键词 + 时间区间 + 密级"检索并高亮命中片段，以便快速定位一件档案。
- US-5：作为档案管理员，我要在借阅申请列表里看到申请人、用途、档案密级，并一键批准/驳回并填写意见，以便留痕审批。

**R2 部门兼职档案员**
- US-6：作为部门兼职档案员，我要只能看到并著录本部门的文件，提交后由档案管理员确认入库，以便不越权、也不背错责任。

**R3 借阅用户**
- US-7：作为借阅用户，我要能检索到公开级档案并直接在线阅 view 或发起借阅申请（填用途、期望归还日期），并能看到审批进度，以便不跑腿也能查到资料。
- US-8：作为借阅用户，我要能查看自己的借阅历史与待归还提醒，以便按时归还、避免逾期。

**R4 领导/审批人**
- US-9：作为领导，我要能看到馆藏总量、年度进馆量、借阅热度等图表报表，并可导出 Excel/PDF 打印，以便向主管单位汇报。

**R0 系统管理员**
- US-10：作为系统管理员，我要能建立用户、分配角色与数据范围、查询全部操作日志、配置每日自动备份并做恢复演练，以便系统安全可控、出事可追溯可回滚。

**P1/P2**
- US-11：作为档案管理员，我要能把往年约 100GB 的存量档案（含目录 Excel + 扫描件目录树）批量导入并自动匹配挂接，以便不必逐条重建。
- US-12：作为档案管理员，我要能做专题编研（挑选档案组成专题、生成大事记与组织沿革），以便对外提供编研成果。
- US-13：作为用户，我要能用自然语言提问"2023 年有哪些关于 XX 的会议纪要"，系统基于档案知识库回答并给出出处链接，以便降低查档门槛。

### 5.4 借阅业务规则细化（F-06 子规则，研发/QA 对齐用）

**借阅状态机**：`草稿 → 待审批 → 已批准 → 已借出 → 已归还`；旁支：`已驳回`、`已取消（申请人撤回）`、`已逾期（由已借出派生）`。

**借期与续借规则（v1.0 口径，已与研发确认）**

| 编号 | 规则 | 口径 | 说明 |
|---|---|---|---|
| BR-06-1 | 借期上限 | **借阅总借期 ≤ 90 天** | 以「应还日期（expectReturn）」为唯一权威字段，其语义为**最终到期日**（绝对日期），不做分段记录 |
| BR-06-2 | 续借次数上限 | **≤ 1 次** | 续借后 `renewalCount = 1`，再次续借请求直接拒绝并提示「已达续借次数上限」 |
| BR-06-3 | 续借校验逻辑 | `新应还日期 = 原应还日期 + 续借天数`，校验 `新应还日期 − 借出日期 ≤ 90 天` | **决策：采用"总借期上限"语义**。即剩 70 天再续 30 天（合计 100 天）**应予拒绝**，提示「续借后总借期将超过 90 天上限，请缩短续借天数」 |
| BR-06-4 | 逾期状态下的续借 | **不允许** | 已逾期单据必须先归还，再重新申请，避免逾期被续借掩盖 |
| BR-06-5 | 待审批状态下的续借 | **不允许** | 仅 `已借出` 状态可续借 |
| BR-06-6 | 续借是否需重新审批 | **不需要，续借直接生效**（v1.3 封版改判） | 续借是同一用户对同一档案的已审批关系延续，且受 BR-06-1 总借期硬约束；新审批单需新增状态机分支，代价高于收益。**替代要求**：必须记录续借日志（操作人/时间/原应还日/新应还日/续借天数/借出日）与 `renewalCount`，保证可追溯；接口预留「校验—生效」两段式扩展位，便于未来接入审批 |
| BR-06-7 | 单次续借天数下限 | ≥ 1 天 | 0 天或负数视为非法入参 |

> **为什么选"总借期上限"而非"单次上限"**：`expectReturn` 是绝对日期字段，其 schema 语义就是「最终应还日期」。若改为"单次上限"，字段无法表达"某区间属于第几次续借"，只能靠审批记录反推，导致逾期计算、借阅台账、统计报表三处逻辑全部复杂化。档案行业惯例亦以"总占用时长"管控，避免单件档案被长期占用。
>
> **研发落地要求**：`borrow.service.ts` 的 `assertExpectReturn()` 语义即本表 BR-06-1/BR-06-3，请在函数注释中明确写「校验借阅**总借期**上限（含续借累计），非单次借期」。**无需修改数据模型与 DTO。**
>
> **前端提示文案（建议统一）**：`借期自借出日起最长 90 天，可续借 1 次，续借后总借期仍不得超过 90 天。`

### 5.5 业务参数体系（F-14 系统参数与字典 · 子能力）

> **【文档职责分工约定】**（主理人最终裁定）
> - **参数「命名、取值、确认级别」以 `系统架构设计.md` §4.3 为唯一权威**（点分下划线命名，如 `borrow.max_total_days`）；`packages/shared` 的 `PARAM_DEFS` 为代码侧唯一定义源，后端常量/种子数据/管理端一律引用它，禁止手写字符串。
> - **PRD 5.5 提供产品侧口径**：参数化原则、确认优先级与理由、变更影响、存量生效口径。PRD 表内取值与 §4.3 保持一致，供评审会议议程使用。
> - 若出现不一致：**以 §4.3 为准**，PRD 同步修订，并作为缺陷记录。

**背景**：本系统有大量"业务策略数值"（借期天数、保留期、超时阈值等）不是硬编码逻辑，而是**单位管理制度的外化**。硬编码会导致单位评审后调整口径必须改代码发版。故统一纳入 F-14，由 `sys_param` 参数表 + 参数缓存 + 管理端维护页承载。

#### 5.5.1 参数化设计原则（产品侧要求）

| 编号 | 原则 | 说明 |
|---|---|---|
| PR-P1 | 全部可配置 | PRD 5.5 列出的全部 22 项参数必须支持管理端在线修改，**业务代码禁止出现策略字面量**（`BORROW_RULES` 等常量对象必须改为读参数表） |
| PR-P2 | 变更即时生效 | 保存后 ≤ 60s 内全节点生效（依赖参数缓存主动失效） |

| PR-P4 | 范围校验 | 每参数定义合法区间，越界拒绝保存并提示，**禁止静默落库** |
| PR-P5 | 分级授权 | 安全类参数仅 R0 系统管理员可改；业务类参数可授予 R1 档案管理员（见 3.2 权限矩阵） |

| `preview.*`（水印/下载） | 全部在线预览的水印渲染、下载按钮显隐、下载审批流是否触发；**关闭水印将削弱截图追溯能力**，涉密档案不建议关闭 | 单位保密部门、全体用户（界面变化需公告） |
| `recycle.retention_days` | 误删恢复窗口缩短将**永久失去挽回能力**；缩短后存量已删除数据是否立即清理需明确（见 5.5.6 D-2） | 档案管理员（培训强调谨慎删除） |

| `backup.keep_copies` | 备份保留份数减少将降低可回溯时间点范围，直接影响 M7（RPO/RTO）达成；**须先确认备份区容量** | 运维 + 单位信息化主管部门 |
| `log.retention_years` | 缩短将导致审计举证期不足；延长将显著增加存储占用（7.2 节按 3 年测算 22GB） | 单位档案/审计主管部门 |

#### 5.5.4 与架构 §4.3 的对齐状态（**已对齐，无需跟踪项**）

> **状态：✅ 22 项全部对齐（架构师确认）**。架构 §4.3 已按 PRD 5.5.2 整体重写对齐，并已收录第 22 项 `borrow.overdue_remind_days`（3 天 / 0–30 / 0=不提醒 / 🟡 / grp=borrow），消费方注明"催还提醒任务（`dueSoon` 取数范围与文案）"。**主表计数与 T02 验收要点均同步为 22 项。**

**机制性防漂移（架构师设计，优于文档约定）**：
- 架构 §4.3 新增「key 命名规范（权威）」段落，规定 **`packages/shared` 的 `PARAM_DEFS` 为唯一定义源**；
- 后端 `PARAM_KEY` 常量、种子数据、管理端全部**引用/镜像 `PARAM_DEFS`，禁止手写字符串**；
- 效果：改一处源头，编译期即可发现引用断裂，「文档—常量—种子」三处漂移被机制根除，不再依赖人工比对。

**key 命名规范**：`模块.属性_下划线`（如 `borrow.max_total_days`）。原代码中 11 个旧式 key（`preview.watermark.enabled`、`audit.retention.months` 等）由研发在参数化改造中迁移。

**提醒 cron 明确不参数化**：`@Cron('0 0 9 * * *')` 保持硬编码。与 `borrow.overdue_scan_cron` 性质不同——后者影响逾期状态判定（业务敏感），前者仅为发通知时点，改动不影响业务正确性，单位调整概率极低。架构 §4.3 消费方列已注明，**防止后来人"画蛇添足"增加参数**。

**存量 key 迁移的两类风险（架构 §4.3 已立约）**：
1. **改名即改值**：`borrow.renew.max`(2) → `borrow.max_renewal_count`(1)，值须同步修正，否则续借次数翻倍
2. **单位换算**：`audit.retention.months`(36) → `log.retention_years` 必须 `value/12` 取整（36→3），**禁止直接搬值**，否则变成"36 年"

**`preview.download_mode` 默认值待定**：架构默认 `disabled`（沿用"关"），PRD Q4 建议 `approval`（预览 + 审批下载）。**该项属 🔴 待单位确认**，确认后只改参数值、不改代码。

#### 5.5.5 参数间依赖约束（产品侧要求，研发落地必检）

单参数区间校验不足，以下跨参数组合会自相矛盾，保存时须统一校验并**一次性返回全部冲突**：

| 约束 | 规则 | 违反后果 |
|---|---|---|
| C-1 | `borrow.default_days` ≤ `borrow.max_total_days` | 申请页预填即超限，用户无法直接提交 |
| C-2 | `borrow.max_renewal_days` ≤ `borrow.max_total_days` | 单次续借上限超过总借期上限，规则自相矛盾 |
| C-3 | `backup.keep_copies` × 单份备份体积 ≤ 备份区可用容量 | 备份写满磁盘，后续备份静默失败 |
| C-4 | `log.retention_years` 变更须同步触发存储容量复核提示 | 日志膨胀导致库盘告警甚至写满 |
| C-5 | **权限变更必须走「主动失效通道」即时清除权限快照**；缓存 TTL 仅作兜底，不得作为生效依据。**P0 必须实现，不接受降级为 TTL 自然过期** | 撤销权限后仍可访问敏感档案 —— **安全漏洞**，无签字豁免通道 |

#### 5.5.6 参数变更对存量数据的生效口径（**已定稿 · 主理人批准 · G-1 + D-1~D-7**）

> **状态：已批准并封版，作为架构与研发的唯一口径。** 原则：**安全类参数立即生效（含存量会话与在途请求）；数据保留类参数只对增量生效（存量等定时任务自然处理）。**
> 主理人裁定：**D-1 ~ D-5 定稿**；D-6 / D-7 为同原则下的补充项一并通过；**D-3 经复议改判为「存量按签发值走完」**（见下表）。G-1、D-2 新口径一并批准。
> **本文档就此真正封版，不再接受非缺陷类变更。**

**总则（G-1，覆盖 D 系列的解释优先级）**：

> **参数变更不回溯已完成的业务行为**——已生成的借阅单、已归档的档案、已写死的应还日，均按发生时的规则继续履行；参数只影响**变更后新发生的判定**。
> **唯一例外**：安全类参数（权限、密级、水印/下载控制）必须立即生效，且须主动失效相关缓存，不得等待 TTL。

| 编号 | 参数类别 | 场景 | 生效口径 | 理由 |
|---|---|---|---|---|
| D-1 | 数据保留类 | 借期上限缩短 | **仅对新增借阅申请生效**，在途单据按原约定履约至归还 | 在途单据的应还日已告知用户并可能张贴在原件上，中途变更会出现"昨天合规、今天逾期"，引发投诉 |
| D-2 | 数据保留类 | 回收站保留天数变更 | **到期时刻 = 删除时刻 + 当前保留天数**，实时计算不回溯。改小后已超期项在**下次巡检时**清理（非立刻、非等满旧值）；**恢复操作同样按新值判断**，已超期项即使仍在库中也不可还原 | 语义符合管理员直觉（"从现在起只保留 7 天"），且避免保存参数瞬间触发全表清理；恢复与清理口径一致，防止"清理前能还原、清理后不能"的随机性 |
| D-3 | 安全类 | 会话超时缩短 | **新值仅对变更后签发的会话生效**；存量会话按**签发时记录的**超时值走完，不强制登出 | **已复议改判（主理人批准）**。会话超时是「防闲置」机制而非权限控制，真正的撤权风险由 D-4 主动失效通道覆盖，立即踢出的安全收益被高估；而批量著录场景下未保存内容丢失是实在的数据损失 |
| D-4 | 安全类 | 权限撤销 / 角色变更 / 密级授权变更 | **立即生效**（主动失效通道，见 C-5） | 安全类参数，不允许任何延迟窗口 |
| D-5 | 数据保留类 | 备份保留份数减少 | 仅清理超出份数的最旧备份，**保留最新一份不可删** | 防止误设极小值导致备份全清空 |
| D-6 | 安全类 | 预览水印开关 / 下载控制变更 | **对存量会话与后续所有预览/下载请求立即生效** | 涉密防护要求，不允许"改之前打开的页面继续无水印"的窗口期 |
| D-7 | 数据保留类 | 日志保留年限缩短 | 仅对增量生效，存量按归档任务周期处理 | 同 D-2，避免瞬时大规模删除日志导致审计断档 |

**研发落地要求**：D-3 / D-4 / D-6 三项必须绕过参数缓存（或强制缓存失效后读取），不得因 60s 缓存导致延迟；D-1 / D-2 / D-5 / D-7 须在定时任务中读取当前参数值，不做历史快照。

> **【口径澄清 · 缺陷类修订】** G-1 总则与 D-3/D-4/D-6 的「立即生效」存在字面张力，架构师已在 `系统架构设计.md` §4.3 拆为三层落地口径，**本处按该三层口径解释，不构成对 G-1 的推翻**：
> 1. **读取生效**：参数新值能否被读到。`security.*` / `preview.*` 直读 DB 零窗口（PR-P8 直读）；其余 60s 缓存 + 主动失效。这是「变更后无旧值残留」，与「存量对象是否作废」是两个独立问题。
> 2. **存量失效**：已存在对象（会话 / 快照 / 在途请求）是否作废。**仅 D-4（权限）/ D-6（水印/下载）需要**。
> 3. **判定生效**：新业务判定用新值、不回溯。D-1 / D-2 / D-5 / D-7 及 **D-3** 均属此类。
>
> **映射关系**：D-1/D-2/D-5/D-7 = 仅第 3 类；**D-3（会话超时）= 第 1+3 类**——存量已签发会话按签发时值走完、不强制下线，新登录/刷新签发时按新值；**D-4/D-6 = 三类全占**。
>
> 即：G-1 的「安全类立即生效」实际只约束 **D-4 / D-6**。两条验收硬句：**「改参数后立即 401」禁用**（D-3 会写反）；**「撤权后下一请求即 403」仅适用于 D-4/D-6**（其余写不到这么硬）。
>
> *与 `系统架构设计.md` §4.3 三层口径同构，两处表述已收敛一致。*

> **P0 实现要求（QD-1）**：会话记录必须保存**签发时的超时值**（`session.timeoutMinutes`），D-3 的"存量按签发值走完"依赖此字段，属 P0 必做而非可选项；同时便于审计追溯每个会话的有效期依据。

### 7.2 存储容量估算

**基线假设**：1,000,000 档案条目（件级）；电子文件 100 GB；日均新增 300 条、约 30GB/年。

| 项目 | 计算 | 结果 |
|---|---|---|
| 条目主表 + 著录字段 | 100 万行 × 约 2KB（含变长字段） | ≈ 2 GB |
| 关联表（卷-件、文件挂接、借阅、日志等） | 约主表 2.5 倍 | ≈ 5 GB |
| 全文索引（ES） | 约原文 1.2 倍，含向量位预留给 P2 | ≈ 8 GB（预留至 15 GB） |
| 电子文件存储 | 现有 100 GB + 副本/备份 | 原始 100 GB，**含备份 ≥300 GB** |
| 缩略图/预览转换缓存 | 约原文件 8% | ≈ 8-10 GB |
| 操作日志（3 年） | 日均 2 万条 × 1KB × 1095 天 | ≈ 22 GB |
| 备份（每日全量 × 保留 30 天，含去重） | 数据库 ~8GB + 文件增量 | ≈ 500 GB-1 TB（建议独立磁盘/网络存储） |
| **合计建议容量** | 在线数据 150 GB + 备份区 1 TB | **磁盘 ≥2 TB（主）+ ≥2 TB（备份）** |

**扩展预留**：按 3 年增长（条目至 300 万、文件至 400GB），建议数据库与文件存储分离部署，文件存储走 NAS/对象存储（MinIO），支持横向扩容。

### 7.3 架构预留（RAG/LLM 扩展位）

- **文本抽取管线**：电子文件入库即抽取纯文本（PDF/Office/TXT/EPUB/MOBI）→ 落 `document_text` 表 → 供全文索引与后续向量化复用。
- **向量库接口**：定义 `EmbeddingProvider` 与 `VectorStore` 抽象接口，默认实现对接本地向量库（如 PgVector / Milvus），P0 阶段只留接口不部署，P2 直接插拔。
- **知识库服务**：预留 `/api/kb/*` 命名空间与知识库元数据表（知识条目、来源档号、密级、版本）。
- **模型调用网关**：统一 `LLM Gateway` 配置（模型地址、密钥、超时、内容过滤），支持私有化部署，确保数据不出内网。
- **密级过滤前置**：任何检索/问答结果在返回前必须过同一套权限与密级过滤器，避免 RAG 越权。

### 7.4 其他非功能

| 项目 | 要求 |
|---|---|
| 兼容性 | Chrome/Edge 最新两个大版本；国产浏览器内核适配（P2 与信创同步）；分辨率 1366×768 起 |
| 可维护性 | 模块化分层，关键业务有单元测试（覆盖率 ≥60% 核心域）；日志分级；健康检查接口 |
| 可迁移性 | 支持从原系统导入（Excel/CSV/SQL 导出 + 文件目录树），迁移工具独立可重跑 |
| 部署 | Docker Compose 一键部署（单机）；可选 K8s 编排；配置外置化 |

### 8.3 关键交互原则

1. **一眼可判**：列表页必须直接显示档号、题名、密级、状态，不点开即可定位。
2. **少点可达**：常用操作（预览、借阅、著录）在结果行内直接提供按钮，目标 3 次点击完成主流程。
3. **不丢数据**：著录表单自动保存草稿（30s/切页触发）；批量操作前明确提示影响范围。
4. **状态可见**：借阅、著录、导入等长流程均以状态标签 + 进度条呈现，禁止"白屏等待"。
5. **权限显性**：无权限操作按钮置灰并给出 `title` 说明原因（如"密级不足"）。
