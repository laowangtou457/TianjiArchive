## 一、VMware 虚拟机准备（缺一不可）

| 项 | 要求 | 说明 |
|---|---|---|
| 客户机 OS | Windows Server 2022 Standard（桌面体验） | 2022 桌面体验版自带完整 PowerShell 5.1 与 DISM |
| vCPU | ≥ 4 核 | **必须勾选「虚拟化 Intel VT-x/EPT 或 AMD-V/RVI」**（VM 设置 → 处理器 → 虚拟化引擎）。没有这一项，客户机内 WSL2 起不来（HypervisorPresent 预检会 FAIL） |
| 内存 | ≥ 12 GB（建议 16） | WSL2 默认吃 50% 宿主内存，编排器会写 .wslconfig 上限 |
| 磁盘 | ≥ 100 GB | Windows 本体 ~40GB + C:\tianji（WSL vhdx + 数据卷）+ 镜像 tar 暂存 |
| 网络 | NAT 或桥接均可 | 验证 S5 LAN 自测建议桥接；纯 NAT 也能装完（S5 会跳过 LAN 自测并 WARN） |

**宿主注意（本机实测环境，2026-11-13 更正）**：宿主 Windows 已启用 hypervisor
（Docker Desktop 的 WSL2 后端 → `VBS 状态=2`、`HvHost`/`vmcompute`/`WslService` 均 Running）时，
VMware 17.x 与 Hyper-V 共存（WHP 模式）**不支持嵌套虚拟化**——客户机内 `HypervisorPresent`
恒为 `False`，WSL2 起不来，S1 预检第 6 项与 S2 必挂。
（本节 v1.0 曾写「嵌套虚拟化仍可用」，是**未验证的推断，已证伪**。）

→ **验证前必须让 VMware 拿到原生 VT-x**（管理员 PowerShell，随后重启）：

```powershell
bcdedit /set hypervisorlaunchtype off
Restart-Computer
```

⚠️ **只做 `bcdedit` 往往不够**（2026-11-13 实测踩中）：Windows「内核隔离 → 内存完整性」开着时，
重启后 hypervisor 会被重新拉起，VMware 启动时报「此平台不支持虚拟化的 Intel VT-x/EPT」+
「模块"HV"启动失败」。必须同时关闭：
**设置 → 隐私和安全性 → Windows 安全中心 → 设备安全性 → 内核隔离详情 → 内存完整性 = 关**，再重启。
重启后在宿主 `(Get-CimInstance Win32_ComputerSystem).HypervisorPresent` 应为 `False`；
进 guest 后同一命令应为 `True`。

代价：验证期间宿主 Docker Desktop / WSL2 不可用（天玑与 mirror-canvas 容器会停，数据在
`E:\docker-data` 不受影响）；验证完 `bcdedit /set hypervisorlaunchtype auto` + 重启恢复。

ISO：微软官网 `Windows Server 2022 zh-cn ISO`（评估版即可，180 天足够验证），本机在
`E:\iso\zh-cn_windows_server_2022_eval_x64.iso`（5,478,957,056 B）。

**本机现成素材（2026-11-13 备好，位于仓库之外）**：`E:\vm-win2022\` 下有可直接双击打开的
`tianji-win2022.vmx`（12GB / 4vCPU / 120G 增长盘 / NAT / ISO 已挂 / 开机顺序 CD→HDD，
含 PCIe 根端口组与 `vhv.enable=TRUE`），配套 `tianji-win2022.vmdk` 与素材光盘
`tianji-media.iso`（Windows 安装包 zip + 镜像 tar + sha256 清单，免共享文件夹）。
已实测：vmx 可开机、可从 ISO 引导进 Windows 安装界面；宿主 hypervisor 未关时会被
`vhv.enable` 挡下并提示「此平台不支持虚拟化的 Intel VT-x/EPT」——**这是预期的硬闸，不是配置错误**。
制作与踩坑细节见 `E:\vm-win2022\操作单.md`。

## 二、包传输与校验

1. 把 zip（699MB）+ `tianji-offline-images.tar`（1.5GB）拷入 VM（共享文件夹 / 拖拽均可）；
2. VM 内 PowerShell 校验 zip 完整性：
   ```powershell
   Get-FileHash .\tianji-server-setup-windows-amd64-1.0.0.zip -Algorithm SHA256
   # 必须等于 521f3604e6524d41de082b281f7d6bcef0e93ff61f98a32296ad1c7934eeb515
   ```
3. 解压 zip 到 **不含空格和中文** 的路径（如 `D:\tianji-setup\`）；
4. 镜像 tar 放到与服务端安装向导同目录（向导 S5_IMponP 装载时选它）。

## 四、本次真机踩坑实录（13 条，全部已修源码）

> 只列「静态检查发现不了、只有真机才暴露」的。每条给出症状 → 根因 → 修法，供换机重验时对照。

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | S2 后 `WSL_E_WSL_OPTIONAL_COMPONENT_REQUIRED` | 只启用了 `VirtualMachinePlatform`，漏了 Pico provider 所需的 `Microsoft-Windows-Subsystem-Linux`；且启用后**必须重启**才生效 | S2 改为双特性幂等循环启用 |
| 2 | `wsl: Expected ' ' or '\n' in /etc/wsl.conf:1`，systemd 从未生效 | PowerShell 双引号里写了字面量 `\n`（PS 的换行是反引号 `` `n ``） | 改 `` `n `` 拼接 |
| 3 | S4 `cp: cannot stat '/mnt/C/tianji/...'` | `WslPathOf` 保留盘符大写，而 WSL2 固定挂 `/mnt/c` | `ToLowerInvariant()` |
| 4 | `.wslconfig` 每行报「-N 无效」，WSL 退回物理内存 50% | 缺 `[wsl2]` 段头，所有键被忽略 | 补段头 |
| 5 | S1 第 10 项内存 FAIL（MemTotal 6GB） | 上一条导致；修好后 8GB 上限又只给到 ~7.4GB（内核开销），仍不满足 ≥8GB 判据 | 内存梯度 ≥16G→12GB / ≥12G→10GB，写后 `wsl --shutdown` |
| 6 | S3_DOCKER `perl depends on perl-base (= 5.34.0-3ubuntu1.9)` | Windows zip 内嵌 11-10 的 .run（85 deb，无 perl-base） | 用 11-12 的 .run（86 deb）重打 Windows 包（本次已做） |
| 7 | 向导 S10 已 DONE 但编排器永不收敛 | S4 用 `$proc.WaitForExit()`，而向导 S10 后是**常驻 Web 服务** | 改轮询 `/var/lib/tianji-install/state.json` 的 `steps.S10_DONE.status` |
| 8 | S5 取不到 WSL IP | `[Console]::OutputEncoding` 切换在计划任务/重定向环境不可靠 | `ProcessStartInfo` 字节流 + Unicode/UTF-8 双解码 |
| 9 | S5 LAN 自测报 `[System.Byte] 不包含名为 Trim 的方法` | `-UseBasicParsing` 下 `Content` 是 `Byte[]` | 统一归一化为字符串 |
| 10 | S6 `无法将参数绑定到参数"Path"，因为该参数是空值` | `$MyInvocation.MyCommand.Path` 在函数作用域为 `$null` | 用 `$PSCommandPath` |
| 11 | S7 冒烟 1/3 FAIL、2/3 PASS（同端口） | `localhost` 在 Server 2022 优先解析 `::1`，而 `v4tov4` 的 `0.0.0.0` 规则**不覆盖回环流量** | URI 改 `127.0.0.1`；portproxy 补 `listenaddress=127.0.0.1` 规则 |
| 12 | S7 2/3 断言恒 null | `/api/health` 实际结构是 `data.status` + `deps[].name == "objectStorage"` | 按真实结构重写断言 |
| 13 | boot.sh 报 `set: -\r invalid option`（rc=127） | here-string 保留 CRLF，base64 忠实带进 Linux | base64 前 `.Replace("`r`n","`n")` |

**另附两条平台级发现（不是脚本缺陷，但会击穿验收）**：

- **A. WSL2 实用 VM 在无附着会话时自动关闭**：8 个 docker 容器不算活动会话。实测 `PID 1 systemd` 的
  `ELAPSED` 每次只有 12–21 秒 = 每次调用都是冷启动。修复：boot 末尾常驻 `sleep infinity` 会话，
  且计划任务 `ExecutionTimeLimit = 0`（原 `PT1H` 会在一小时后杀掉 keep-alive）。
- **B. 冷启动耗时 35–60 秒**：systemd 引导 + dockerd + 8 容器 restart。boot 包装需 12×5s 预热，
  否则开机瞬间取 IP 必失败（`portproxy rc=4`）。

## 五、已知风险点（验证时重点盯）

1. **S2 重启时序**：DISM 启用特性后编排器退出码 7；重启后续跑是否正确跳过已 DONE 步骤。
2. **WSL IP 漂移**：V6 重启后 WSL IP 会变，portproxy 由 boot 任务刷新——若 LAN 不通，先看
   `C:\tianji\logs\boot-<日期>.log`（编排器留痕）与 `netsh interface portproxy show all`。
3. **systemd 引导时长**：boot.sh 上限 300 秒；实测冷启动 35–60 秒。若超时 FAIL，先确认
   boot 包装的预热（12×5s）是否生效。
4. **WSL2 VM 被 idle 关闭**：见 §四 平台级发现 A。判据：`wsl -d TianjiArchive -u root -- ps -o etime -p 1`
   的 `ELAPSED` 若只有十几秒，说明 VM 是刚冷启动的，容器还没起来。
5. **杀软/Defender**：若客户机装了三方杀软，ext4.vhdx 扫描可能拖慢 IO——登记现象即可。
6. **S4 Web 向导交互**：`.run` 无 TTY 时是否正确走 Web 向导（Go 安装器 §3 设计）；
   若进入 TUI 交互模式，截图登记，回宿主侧裁定。
